DocuChat

Guided bootcamp project

How a question travels through the system

  1. Client
  2. Route
  3. Controller
  4. Service
  5. Repository
  6. Postgres + LLM

Layered architecture: routes handle HTTP, controllers parse input, services hold business logic, repositories are the only layer that touches the database.

Problem

Answers pulled from long documents are only useful if you can trust them, and a language model will happily invent one.

Solution

A document Q&A backend that answers only from the asking user's own documents, saves source citations with each answer, and replies with a fixed "nothing relevant found" message, without calling the model, when retrieval comes back empty.

AI component

Retrieval: keyword matching over document chunks, limited to the user's own documents that have finished processing.

Generation: the retrieved chunks go to an LLM with instructions to answer only from the excerpts, treat them as reference material rather than instructions, and not invent facts or sources. Output is capped at 500 tokens.

Not built yet: embedding-based (semantic) retrieval.

Engineering decisions

  • Every retrieval query is filtered by the authenticated user's ID.
  • Requests and environment config are validated with Zod, so bad input is rejected early.
  • Chat routes sit behind JWT middleware, and a conversation you do not own returns 404.
  • The LLM call lives behind one function, generateAnswer(question, chunks), so the provider can change without touching chat logic.

Stack

  • TypeScript
  • Node.js
  • Express
  • PostgreSQL
  • Prisma
  • Zod
  • JWT
  • OpenAI SDK

Challenges

My OpenAI account has no credits and I cannot buy any, so the first live generation call failed with a 429. I am replacing the provider with a free one. I also tried running a model locally with Ollama; its API would not respond on my machine, so that route is parked.

What I learned

Passing a compile check does not prove a feature works. I tested retrieval, ownership checks and message history through the real endpoints. The AI call is the one piece that has not yet returned a live answer.

Evidence

Tested by hand against a running server and a real PostgreSQL database: relevant questions return the matching chunk, irrelevant questions and wrong-user queries return nothing, follow-up messages reuse a conversation, history returns in order, and another user's conversation returns 404.

AI-POWERED PUBLIC TRANSPORTATION PREDICTION SYSTEM

Group project

Problem

Many people in Nigeria spend a lot of time waiting for buses and other forms of public transport. They also face heavy traffic, overcrowded vehicles, and uncertainty about how long their journey will take. Transport operators also find it difficult to know where more of their services will be needed at different times of the day. This leads to wasted time, overcrowding, and poor transportation services.

Solution

We propose an AI-powered transportation system that helps people know how long they may wait for transport and how long their journey may take. The system can also tell transport operators when and where many passengers are likely to need their services, helping them be available where they are needed.

How it works

~A passenger enters where they are going.

● The system checks available transport routes and current information.

● AI studies the information.

● The system estimates the waiting and travel time.

● The passenger receives the information and can choose the most suitable option.

AI component

AI will be used to make predictions.

The system can study previous traffic conditions, the number of passengers, time of day and current road conditions to predict:

● How long a passenger may wait for transport.

● How long a journey may take.

● Which routes may be very busy.

● Where more passengers are likely to need buses/keke.

The normal software can show routes and information, while AI helps predict what is likely to happen.
